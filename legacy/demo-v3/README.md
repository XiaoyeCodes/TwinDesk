# 浏览器内操作Windows应用 — 可行性验证Demo

这是一个最小可行性验证demo，用来验证核心链路：**窗口画面捕获 → WebSocket推流 → 浏览器显示 → 浏览器操作转发回窗口**。

先用记事本跑通，原理通了之后再换成UG测试，避免一开始就在UG这种重型软件上排查问题。

## 运行步骤

### 1. 安装依赖（Windows + Python 3.9+）

```bash
pip install websockets mss pygetwindow pyautogui pillow pywin32
```

### 2. 打开一个记事本窗口
Windows开始菜单搜索"记事本"打开即可，不要最小化。

### 3. 启动后端服务

```bash
python server.py
```

看到 `WebSocket服务已启动: ws://localhost:8765` 说明启动成功。

### 4. 打开前端页面
直接双击 `index.html` 用浏览器打开（Chrome/Edge均可）。

正常情况下几秒内应该能在网页里看到记事本的画面，鼠标移动、点击、打字都能同步过去。

## 验证成功后，如何切到UG测试

打开 `server.py`，把这一行：

```python
TARGET_WINDOW_TITLE = "记事本"
```

改成UG窗口标题里能唯一识别的关键字（比如UG打开一个模型后标题栏显示的软件名关键词），重启 `python server.py` 即可。

## 已知局限（demo阶段，非生产版本）

这版代码是为了**最快验证原理可行性**写的，离能上生产还有明显距离，主要体现在：

- **画面捕获方式较原始**：用的是屏幕区域截图（mss），不是针对窗口句柄的DXGI Desktop Duplication，如果目标窗口被其他窗口遮挡，捕获到的会是遮挡后的画面。这也是为什么前期建议记事本窗口保持在最前面测试。生产版本需要换成基于窗口句柄的专用捕获API（比如`windows-capture`库），才能做到"哪怕被遮挡也能拿到干净画面"以及性能更好。
- **按键映射不完整**：`KEY_MAP`里只覆盖了常用按键，中文输入法、组合键（Ctrl+S之类）目前没有特殊处理，能测试基本的英文打字和方向键、回车、退格。
- **没有做窗口裁剪**：目前是整个窗口一起传，UG的话工具栏、菜单栏等非绘图区也会一起显示，还没做"只显示绘图区"的裁剪逻辑。
- **单帧率固定15fps**：为了本机验证阶段的稳定性先写死，后面可以根据实际测试情况调整或做动态帧率。
- **未做鉴权和多用户支持**：这版只考虑单人本机验证，没有会话管理、权限校验这些。

## 下一步建议

1. 先用记事本把整条链路跑通，确认WebSocket通信、画面刷新、鼠标键盘转发这几个环节都没问题
2. 换成UG测试，重点观察：
   - 3D旋转、缩放时的画面流畅度和延迟感受（这是最大的风险点，值得重点评估）
   - CPU占用情况（用任务管理器盯着看`python server.py`进程和UG进程的CPU占用）
   - 复杂装配体渲染时画面是否明显卡顿
3. 如果验证下来性能可以接受，再考虑往生产方向替换：换用`windows-capture`库做窗口级捕获、加窗口裁剪逻辑、优化编码方式（比如换成H.264硬件编码而不是JPEG逐帧压缩）
